## L-001: Guard engine running/busy state before rotating controller credentials

- Status: confirmed
- Applies when: Changing core startup, hot-reload, or remote control handlers (`LocalDeviceSession`, `EngineController`, `AppStateRemoteHostBackend`, `RemoteDeviceSession`).
- Failure: Triggering remote hot-reload produced `热重载失败：本机 Mihomo 控制接口返回 HTTP 401。` as a blocking modal alert on the host Mac while `ConnectionMonitorService` continued streaming connections normally and the remote client received a premature `"已触发热重载。"` success message.
- Cause: `MainView` hid the local Start button while `isCoreRunning` was true, but `LocalDeviceSession.canStart` and `LocalDeviceSession.start()` did not check `!engine.isRunning`. When a remote client (such as iOS `HomeView`/`RemotePCView`, whose Start button remained enabled) sent `POST /api/v1/engine/start` to an already-running host, `LocalDeviceSession.start()` generated a new random `secret` and replaced `liveProxyStore.controller` before calling `engine.start()`, which then returned early as a no-op at `guard activeHandle == nil, !isBusy`. The running Mihomo process kept its original `secret`, causing subsequent `PUT /configs?force=true` hot-reloads via `liveProxyStore.controller` to fail with HTTP 401. In addition, `RemoteHostBackend.hotReload()` returned synchronously instead of awaiting the reload task, and `RemoteDeviceSession.hotReload()` did not flush debounced profile edits before calling `/api/v1/engine/hot-reload`.
- Missed check: Existing startup and remote-control tests exercised `EngineController.start()` directly or used a stubbed `MockRemoteHostBackend`, missing the real `RemoteAPIHandler -> AppStateRemoteHostBackend -> LocalDeviceSession.start() -> hotReloadFromRemote()` sequence when the core was already running.
- Next time: Enforce lifecycle preconditions (`!engine.isRunning && !engine.isBusy`) inside `LocalDeviceSession.start()`, `LocalDeviceSession.canStart`, and `EngineController.start()` before mutating `liveProxyStore.controller` or `pendingSessionContext`—never rely on SwiftUI button visibility to protect state transitions reachable via Remote API. Keep remote action handlers awaiting bounded completion so errors return in `RemoteActionResult` instead of popping unattended alerts on the host.
- Evidence: `Sources/RouteWeaverRuntime/DeviceSession.swift`, `Sources/RouteWeaverRuntime/EngineController.swift`, `Sources/RouteWeaverRuntime/RemoteServerService.swift`, `Tests/RouteWeaverRuntimeTests/DeviceSessionTests.swift` (`testRemoteStartWhileRunningPreservesControllerSecretAndAllowsRemoteHotReload`, `testRemoteHotReloadSelfHealsStaleControllerSecretFromPersistedEngineConfig`, `testRemoteDeviceSessionHotReloadFlushesPendingProfileEditsFirst`).
- Validation: Executed `swift test` — all test suites passed (`TunHelperProtocolTests` 6/6, `RoutingCoreTests` passed, `RouteWeaverRuntimeTests` 40/40). Live Mac mini deployment requires re-deploying the updated app bundle.
- Updated: 2026-11-26; initial confirmed root cause and regression suite.

## L-002: Enforce width-budget contracts, wrapping headers, and single-line pill invariants across SwiftUI detail views

- Status: confirmed
- Applies when: Adding or editing macOS SwiftUI toolbars, `SectionCard` trailing controls, status pills, metric readouts, or master-detail inspector drawers in `Sources/RouteWeaverRuntime/Views/`.
- Failure: At narrower window widths (860–960 pt), especially when link errors appeared and opened the right-hand diagnostic drawer, `NavigationSplitView` symmetrically sheared ~30 pt off both the left sidebar (cutting off icons and `127.`) and the right drawer/header buttons, while middle topology target cards collapsed to ~156 pt and rendered `StatusPill` and speed strings vertically one character per line (`网\n卡\n直\n连`, `2\n4\n活\n跃`).
- Cause: (1) Single-row `HStack` headers outside `ScrollView` (`NetworkTopologyView.headerToolbar`) accumulated >830 pt of non-wrapping intrinsic width; combined with the 180 pt sidebar, total minimum width (~1010 pt) exceeded `NSWindow`'s 860 pt minimum, causing `NSHostingView` to center-clip the root view on both edges. (2) Subtracting a hardcoded 348 pt right drawer plus a fixed 230 pt + 46 pt left rule column left <160 pt for `targetPipelineCard`. (3) `StatusPill` and inline speed `Text` lacked `.lineLimit(1)` and `.fixedSize(horizontal: true, vertical: false)`, so equal width-sharing inside `HStack` compressed each item to ~20 pt. (4) Unbounded `Picker` controls inside vertical `ScrollView` drawers could widen the inner document past the drawer width and clip right-aligned status labels.
- Missed check: Prior runtime tests only verified that a single `NSHostingView` built with `fittingSize.width > 0` at 960×640 in an idle state, without testing minimum-width windows (900×600), anomaly states (which add extra toolbar buttons and open drawers), or single-line height invariants on atomic pills.
- Next time: Keep `detailView` wrapped in `.isolateHorizontalOverflow(minWidth:)` (`WidthBudgetContainer`), host right-hand drawers inside `AdaptiveInspectorScaffold` (so narrow stages switch to overlay instead of subtracting canvas width) with `.lockScrollDocumentWidth()` on drawer scroll content, place multi-item header actions/badges inside `SplitHeaderBar` + `FlowLayout`, use `StatusPill` / `MonospacedMetricText` (which bake in `.lineLimit(1)` + horizontal `fixedSize`), and add/run `LayoutContractTests` at minimum window dimensions with anomaly states active.
- Evidence: `Sources/RouteWeaverRuntime/Views/LayoutPrimitives.swift`, `Sources/RouteWeaverRuntime/Views/SharedComponents.swift`, `Sources/RouteWeaverRuntime/Views/MainView.swift`, `Sources/RouteWeaverRuntime/Views/Topology/NetworkTopologyView.swift`, `Sources/RouteWeaverRuntime/Views/Monitor/RequestMonitorView.swift`, `Tests/RouteWeaverRuntimeTests/LayoutContractTests.swift` (`testAtomicStatusPillAndMetricTextNeverWrapIntoVerticalCharacterColumns`, `testAdaptiveInspectorScaffoldSwitchesToOverlayBelowBudgetAndDocksAboveBudget`, `testDetailOverflowIsolationAndAnomalyViewsRespectMinimumWindowWidth`).
- Validation: Executed `swift test` — all suites passed (`TunHelperProtocolTests`, `RoutingCoreTests`, `RouteWeaverRuntimeTests` including 3 new `LayoutContractTests`); rebuilt and restarted `routeweaver` via Lumzel `app_preview` (`state: ready`).
- Updated: 2026-11-26; recorded five-layer SwiftUI layout architecture and regression checks.

## L-003: Guard same-path binary installation and keep live TUN core running during authorization prompts

- Status: confirmed
- Applies when: Resolving Mihomo candidate binaries (`CoreBinaryStore.resolveBinary()`) or executing privileged TUN installation/re-sync (`TunHelperManager.authorize()`, `LocalDeviceSession.authorizeTun()`).
- Failure: Clicking "重新同步 / 同步新版组件" in Settings popped up an error alert `install: /Library/Application Support/RouteWeaver/mihomo and /Library/Application Support/RouteWeaver/mihomo are the same file (64)` and left the core stopped while PF Kill Switch remained active, blocking host internet access.
- Cause: (1) Including `TunHelperPaths.installedMihomoURL` (`/Library/Application Support/RouteWeaver/mihomo`) as a candidate in `CoreBinaryStore.resolveBinary()` caused `binary` to equal `installedMihomoURL`, which `TunHelperManager.authorize()` passed directly to `/usr/bin/install src dst` without checking `src == dst` or staging to `.new` + `mv -f`. (2) `LocalDeviceSession.authorizeTun()` stopped the running core *before* running `osascript`, and only restarted in `defer` when `authorized == true`, stranding the machine with PF Kill Switch active whenever `osascript` failed or was canceled.
- Missed check: Unit tests mocked `PrivilegedHelperExecuting` CLI commands and did not validate the generated `authorize()` shell script against `src == dst` or `/bin/sh -n`.
- Next time: Stage binary updates to `<dst>.new` followed by atomic `/bin/mv -f` when `src != dst` (and skip `install` in favor of `chown`/`chmod` when `src == dst`), validate generated shell scripts with `/bin/sh -n` in unit tests, and perform atomic root installation *before* restarting a running core so prompt cancellation or failure never interrupts an active gateway or triggers PF Kill Switch lockout.
- Evidence: `Sources/RouteWeaverRuntime/TunHelperManager.swift`, `Sources/RouteWeaverRuntime/DeviceSession.swift`, `Tests/RouteWeaverRuntimeTests/PrivilegedHelperTests.swift` (`testBuildAuthorizeShellCommandHandlesSameFileAndValidShellSyntax`).
- Validation: Executed `swift test` — all suites passed (including `PrivilegedHelperTests` 7/7 and `RouteWeaverRuntimeTests` 49/49); rebuilt and restarted `routeweaver` via Lumzel `app_preview` (`state: ready`). Live privileged `osascript` prompt execution remains to be verified interactively by the user.
- Updated: 2026-11-26; initial confirmed root cause and shell regression check.
